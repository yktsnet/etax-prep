# Design Decisions

etax-prep の技術選定と設計判断の全文。README の Design Decisions と Tech Stack はここから要点を引いている。

## 既存OSSを使わず自作する

日本の確定申告向けOSSは3系統ある。青色申告決算書＋仕訳帳を備えた帳簿システム、ローカルファーストのPWA仕訳帳、AIエージェント用プラグイン。いずれも複式簿記の道具として後段（決算・帳票・e-Tax）が厚い一方、日々の費用を最小手数で打ち込む入口としては設計されていない。逆に入口が軽いものは家計簿アプリで勘定科目を持たない。

必要なのは入口であり、後段のe-Tax入力は普段から手で行っていて負担ではない。既存OSSの導入は後段を重複させるだけで、入口の課題を解かない。

## 入力を単式のまま受け取り、複式へ変換する

青色65万控除は正規の簿記を要求するため貸借対照表が要る。一方で入力のたびに借方・貸方を指定させると、最小手数という目的を損なう。

事業用の口座・クレカを分けていないため、費用の支払は常に私費立替であり、貸方は事業主借に固定できる。したがって入力は借方の勘定科目のみでよく、仕訳の生成は完全に自動化できる。複式簿記の要件と入力の軽さが両立する。

将来事業用口座を分ける場合に備え、支払手段を `config` から有効化できる余地を残す。

## 金額を税込で保持し、税率区分を自動付与する

消費税の課税方式（免税・2割特例・本則）が未定であり、年末に選びたい。本則を選ぶ可能性を残す以上、費用側にも税率区分が要る。

税率を毎回選ばせると入力が重くなるため、科目別の既定値から自動付与する。既定がほぼ当たるため手数は増えず、後からどの方式でも計算できる。税抜経理は採らない。免税の可能性が残る段階で税抜に倒すと、免税確定時にデータが無駄に複雑になるため。

## 期中は現金主義で入力し、年末だけ発生主義へ寄せる

売上は入金日を計上日として扱いたい。ただし65万控除は発生主義が前提であり、現金主義の特例は10万控除しか取れないため両立しない。

期中は入金日で1行入れ、12月末に年をまたぐ未収・未払だけを決算整理で拾う運用にする。結果は発生主義と一致し、日々の入力は現金主義の軽さを保てる。

## 紙は電子化せず、電子取引データのみ扱う

2024年1月以降、電子取引データ（クレジット明細のスクショ、Web領収書、メール添付PDF）は電子保存が義務である一方、紙で受け取った領収書は原本を紙で保存すれば足りる。スキャナ保存は任意の制度であり、採用すると解像度・タイムスタンプ相当・訂正削除履歴などの要件が発生する。

要件を満たさないまま写真を撮っても原本を破棄できず二重管理になるため、紙は封筒のまま扱わない。アプリが扱うのは電子取引データだけとし、制度上の切れ目と実装の境界を一致させる。

## 取引の削除を物理削除にしない

電子帳簿保存法は訂正・削除の履歴が残ることを求める。行を消すと集計からは消えるが、何をどう直したかが帳簿上に残らない。

取消フラグを立てて集計から外す論理削除を採る。git 履歴と併せて二重に記録が残る。証憑も同じ扱いで、取引からの紐付けを外してもファイル自体は残す。誤って添付したことは削除の理由にならない。

`hi` ではWeb側に編集を実装しなかったが、技術的な困難ではなく必要が薄かっただけである。本アプリでは打ち間違いの訂正が日常的に起きるため、編集経路をMVPへ含める。GitHub API の read-modify-write（取得した sha を添えて PUT）で行い、単独利用のため競合はほぼ起きない。sha 不一致で拒否された場合は再取得してやり直す。

## 帳簿の正本をGitHubリポジトリに置き、DBを持たない

帳簿は追記のみで増え、取消も物理削除ではなくフラグで表す。書き手は本人ひとりで、読み出しは年で絞った全件の集計しかない。同時更新の調停も索引も要らないため、月ごとに分けたJSONLを読んで純関数で集計すれば足りる。

電子帳簿保存法が求める訂正・削除の履歴は、コミット履歴がそのまま満たす。DBへ寄せた場合、この履歴を自前で設計して運用することになる。保存要件のほうがgitの性質と一致している以上、DBは機能を足すのではなく実装を増やす。

保存先をGitHubへ委ねているが、ロックインはしていない。正本は1行1取引のJSONLと証憑ファイルであり、cloneした時点で完全な写しが手元に残る。API経由の読み書きは `core/store-github.mjs` に閉じていて、ローカル実行は同じインターフェースの `core/store-local.mjs` で動く。移行するなら保存先アダプタを1本足せばよい。

## 証憑画像を外部ストレージへ逃がさずgitへ入れる

画像は電子取引データそのものであり、帳簿と分離すると保存性が落ちる。年に数百枚・数十MB程度でgitの負荷にならない。

clone ひとつで帳簿と証憑が揃う状態が、保存要件に対して最も強い。R2 等の外部ストレージは採らない。

## 静的サイト生成を挟まず、素の ESM JavaScript で組む

集計が主役であり、入力直後に数字が反映されるほうが用途に合う。ビルド時集計を挟む Zola 構成は、1件の入力ごとに再デプロイを待つことになり噛み合わない。

ビルドステップを持たない素の ESM で書き、コアロジック（集計・按分・仕訳生成・税計算）をランタイム非依存にする。保存先はアダプタで差し替え、ローカル開発はファイルシステム、本番は GitHub API とする。Cloudflare Pages Functions へそのまま移せる。

## 税率・控除額を設定ファイルへ切り出す

給与所得控除・基礎控除・税率表は毎年改正されうる。コードへ直接埋めると改正のたびにロジックを触ることになり、誤りが混入しやすい。

`config/tax-<年>.json` に年ごとの定数として置き、計算コードは年に依存しない形にする。運用開始前と各年分の申告前に国税庁の一次情報で裏を取る前提とする。

## API を Web 標準の fetch ハンドラとして書く

ローカル開発は node:http、本番は Cloudflare Pages Functions と実行環境が異なる。素直に書くとルーティングと業務ロジックが二重に実装され、片方だけ直す事故が起きる。

`Request → Response` の Web 標準インターフェースでハンドラを1本書き、両者はそれを呼ぶだけの薄いアダプタにする。Node 24 は `Request` / `Response` を備えるため、この形がそのまま動く。差分は保存先（`LocalStore` / `GitHubStore`）だけになる。

ローカルでも `STORE=github` で本番と同じ経路を検証できる。

## 未決

- ダッシュボードの限界税率は、事業所得が青色申告特別控除で頭打ちになっている状態では実態と合わない。経費を積んでも控除が減るだけで税額が動かない領域があるため、限界税率の表示ではなく「あと N 円の経費で税額がいくら動くか」の試算へ置き換えるべきか
- 証憑画像のファイル名規則。取引年月日・金額・取引先を含めて、電子取引データの検索要件の代替とする方向
- 既往分を遡って一括入力する入口の形
- 電子取引データの改ざん防止に用いる事務処理規程の置き場所
